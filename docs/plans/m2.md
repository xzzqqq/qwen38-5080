# M2：NVFP4 eager runner 执行计划

- 对应：[roadmap](../roadmap.md) Phase 1 / M2；日期：2026-10-20。
- 本计划按 [roadmap](../roadmap.md) §6.1 的 M2 要求和 M1 后的调整意见细化执行步骤。
- 目标：在单张 RTX 5080 上得到数值正确、8K 范围内可运行的文本 runner，为 M3 建立性能 baseline 做准备。
- 默认：bs=1、NVFP4 W4A4、GDN state FP32、KV BF16、embedding host BF16、greedy + thinking。
- M2 不设 tok/s 门槛；static cache、CUDA Graph、FP8 KV 和优化 kernel 留到后续阶段。

## 1. 环境与 checkpoint 预检

GPU 操作在 5080 Linux 主机的 full access 环境执行；复用现有 `cuda13` 工具链。

运行前先确认 `CUDA_HOME` 指向 `~/micromamba/envs/cuda13`，并设置
`FLASHINFER_WORKSPACE_BASE=$PWD/.tmp/flashinfer`。系统 nvcc 是 12.4 时，FlashInfer
会把 SM 120 判成“requires CUDA >= 12.8”；默认 cache 写到 `~/.cache/flashinfer` 也可能
不可写。`scripts/m2_preflight.py` 会自动检测这两项。

1. 记录 PyTorch、Transformers、FlashInfer、驱动、CUDA 版本，确认 capability `(12, 0)`，
   Transformers 包含 `qwen3_5`，FlashInfer 可以在实际 GPU 上运行所选 NVFP4 backend。
2. 固定 `gittensor-model-hub/Qwen3.8-27B-NVFP4-RTX5090` 的 revision，保存 config、
   quantization config、safetensors index 和文件 hash；tokenizer/template 使用同一 revision。
3. 从实际 tensor metadata 建立清单：名称、shape、dtype、原始字节数、repack 后字节数和放置位置。
   加载文本模型与 `lm_head`，排除 vision 和未使用模块；所有保留高精度的 tensor 单列，
   包括 `in_proj_a/b`、`conv1d`、norm 等，不能只按名称猜测 dtype。
4. 核实 E2M1 nibble 顺序、block scale、global scale、activation quantization、舍入/饱和规则，
   以及 `alpha` 与 backend scale layout 的关系，写入 `docs/model.md`。
5. 分开核算常驻权重、KV、GDN/conv state、workspace、临时副本和 CUDA/allocator 开销。
   M1 空闲可用约 16.61 GB 仅供预估；实际预算使用当前进程初始化后的 `mem_get_info()`。

**产物**：版本清单、tensor manifest、初版显存账。验证通过后锁定依赖到 `requirements.txt`；
尚未验证的版本或 backend 不写成已支持。

**1b 结果（2026-10-20）**：revision `5b7a687fc8211a5d631c8ca6a593dd37eb26ce33`；
两个 shard 的 CRC32 与 `crc32.txt` 一致；2387 个 tensor 的 manifest 已生成；GPU 文本
权重 14.452 GB，host embedding 2.543 GB，vision 0.921 GB；8K + BF16 KV 估算
15.929 GB，余约 0.68 GB（workspace 仍为占位）。详见 [model.md](../model.md)、
[1b journal](../journal/2026-10-20-m2-checkpoint-manifest.md) 和
`results/m2/20261020T175405-manifest/`。

## 2. NVFP4Linear：先对拍，再测耗时

1. 实现独立的 unpack/dequant reference，先验证 nibble、scale、layout 转换；
   覆盖零值、正负值、量化边界、饱和与 padding，检查 repack 不改变有效量化值。
2. 实现 activation quantization 和 `NVFP4Linear`：packed 权重只在加载时转换一次，
   forward 调用 FlashInfer `mm_fp4`，输出 BF16；高精度例外维持 checkpoint 的约定。
3. 使用 manifest 中 attention/GDN projections、FFN、完整 `lm_head` 的不同实际 shape，
   覆盖 `M=1`（AR）、`M=8`（未来 verify）、`M=128`（prefill）及非整 chunk 的尾块。
4. GEMM 对拍使用相同量化 A/W 经独立 reference dequant 后的 PyTorch 结果；
   activation quantization 另与独立 reference 对拍，避免两边复用错误量化逻辑。
   记录 max absolute error、normalized RMSE、cosine similarity 和非有限值。
   在集成 runner 前，根据输出 dtype 和参考计算固定测试容差、记录依据；失败时定位原因。
5. warmup 后测量 activation quantization + GEMM 的完整路径，另报 GEMM 单独耗时和 workspace；
   固定通过验证的 backend，记录布局及 padding，不依赖未记录的 `auto` 选择。

**产物**：算子实现、reference、测试和 microbench；性能数字附命令、代码 commit、shape、backend。
`M=8` 在此只验证算子可用性，不实现 spec decode。

**§2 结果（2026-10-20）**：`runner/ops/nvfp4/` 完成，backend 固定 `cutlass`；
reference 与 FlashInfer activation quant 的 code diff = 0；真实权重 M=1/8/128/3/17/129
的 nrmse ≈ 0.00166、cosine ≈ 0.9999986，13 个 pytest 全通过。microbench 覆盖
`in_proj_qkv` / `gate_proj` / `lm_head`。JIT 需要 `CPATH` 同时包含
`cuda13/targets/x86_64-linux/include` 和 pip 的 `nvidia/cu13/include`，用
`scripts/m2_env.sh` / `.fish`。详见
[§2 journal](../journal/2026-10-20-m2-nvfp4-linear.md)。

## 3. 拼装 eager 文本 runner

1. 以 Transformers `qwen3_5` 文本模型为骨架，在分配完整 GPU 参数前替换量化 linear，
   按 manifest 逐 tensor 加载。避免完整 BF16 GPU 副本，释放 repack 临时 buffer。
2. embedding 在 CPU gather 后传输所需行；decoder 和 `lm_head` 常驻 GPU。
   检查实际 KV dtype 为 BF16、GDN recurrent state 为 FP32；同时管理 conv state。
3. prefill 默认 chunk size 128，依次更新 attention cache 与 recurrent/conv state；
   只在整个 prompt 最后的位置计算 logits，避免生成整段 vocab logits。
4. 实现显式 eager decode loop：正确推进 position/cache，greedy 选 token，
   按模型 EOS/停止规则结束，并检查 `prompt + output ≤ 8192`。
   使用模型自带 chat template，开启 thinking，不自行拼接模板控制 token。
5. 对照 reference 验证 chunked prefill 与单段 prefill、prefill 后继续 decode，
   以及请求之间 cache/state reset；确认不会跨请求残留状态。

**产物**：loader、文本 runner、可复现的生成入口；M3 可以复用其权重和正确性 reference。

**§3 结果（2026-10-20）**：meta 骨架 + 401 个 `NVFP4Linear` + HostEmbedding 加载成功；
`quantized_linears=401`，加载后 allocated 14.457 GB / reserved 14.556 GB。三条真实
prompt 正常 EOS：math 得到 72，code 含 3 个测试，chat 正好三句。8K
（7680 prompt + 512 decode）peak 15.620 GB allocated / 15.859 GB reserved，
free 0.413 GB。详见 [§3 journal](../journal/2026-10-20-m2-eager-runner.md)。

**开放项**：300-token 单段 prefill 与 `chunk=128` 的 logits cos 0.929、argmax 不同；
mask/position_ids 已排除，分叉从第 1 层 GDN 开始。smoke prompt 都 <128，不受影响；
8K capacity 只验证不 OOM。runner 数值对拍尚未闭环。

## 4. 数值、生成与显存验收

| 检查 | 方法与通过条件 |
|---|---|
| runner 数值 | 固定 M1 三条 prompt 的 token IDs 和每条 16 步续写输入，在相同输入下逐层比较 hidden states、cache/state 和最终 logits，满足预先固定的容差；保存首处偏差，避免自由生成分叉掩盖问题 |
| reference 容量 | reference 与目标执行分开；reference 可逐层 dequant/加载并保存中间结果，不要求整份 BF16 模型驻留 GPU |
| 真实生成 | 复用 `results/payload_{math,code,chat}.json` 的 prompt，greedy、thinking、max_new_tokens=2048；数学答案 72，代码与三句回答合理，thinking 和停止正常；不要求复现 IQ4 的逐 token 输出 |
| context 与容量 | `depth=512 / 7680`，各追加 512 步；容量检查用固定 token 序列，不因 EOS 提前退出；无 OOM、NaN/Inf 或 cache 越界 |
| 峰值显存 | 分别测加载、repack、prefill、decode；每段重置 peak stats，结束同步后记录 `max_memory_allocated()`、`max_memory_reserved()`、`mem_get_info()`，辅以 `nvidia-smi`；区分 PyTorch reserved 与驱动 Reserved |

显存不足时，先排查临时副本和 buffer 生命周期，再把 prefill chunk 从 128 降到 64、32，
每次保留失败记录。仍无法满足 8K 或数值检查时，明确记录阻塞和原因；M2 不标完成。
