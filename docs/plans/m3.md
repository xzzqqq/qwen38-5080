# M3：decode 性能 baseline 执行计划

- 对应：[roadmap](../roadmap.md) §2、§3、§6.1 / M3；日期：2026-10-21，已按实施前 review 修订。
- 状态：计划已写，实施未开始。
- 数值/容量/性能验收可参考 [validation 经验](../validation.md)；gate 由本 plan 定义。
- 目标：建立可复现的 eager / static cache / CUDA Graph 对照，拿到两档 context 的
  decode 速度、时间分布、显存峰值和逻辑 SOL，为 Phase 2 确定优化顺序。
- 主线格式：bs=1、NVFP4 W4A4、KV BF16、GDN recurrent state FP32、conv state BF16、
  embedding host BF16；prefill chunk=128，默认 greedy + thinking。
- M3 不设 tok/s 门槛。FP8 KV、自写 GEMV/GDN/attention kernel、算子融合和 spec decode
  按 roadmap 留到后续阶段；本阶段只做运行管理和 graph capture 必需的适配。

## 1. 冻结 M2 基准与已知限制

1. correctness reference 固定为 `ca1bd2e` 的 `EagerTextRunner`，依赖沿用
   `requirements.txt`；checkpoint revision 固定为
   `5b7a687fc8211a5d631c8ca6a593dd37eb26ce33`。
2. 保留 401 个 `NVFP4Linear(backend="cutlass")`、96 个
   `ShapeStableLinear(block_m=128)`、当前 GDN/conv fallback 和 chat template。
   每次只引入一种执行方式变化，reference 的权重和算子语义保持固定。
3. 复用 [M2 关闭记录](../journal/2026-10-21-m2-close.md) 的 smoke、numeric、capacity
   结果。M2 的约 11–12 tok/s 是诊断值；M3 用下述统一计时入口重新测 eager。
4. activation quant 的独立 reference 差异保留为已知限制，归因诊断移至 **Phase 2
   自写 norm/quant kernel 的前置工作**，不阻塞沿用 FlashInfer 的 M3。届时保存失败的
   16-element 输入 block、`input_scale`、双方 scale/code、token/layer 位置及距舍入
   边界的距离；汇总指标不能单独证明 midpoint 归因。若实际量化路径改变，需重新冻结
   reference 并重跑受影响的验证，不能沿用旧 baseline 声称收益。
5. 四模式基线完成后，可以单独 A/B 预计算 `alpha/divisor` 等常量；在与原 forward
   相同的设备和 dtype 下计算，并验证 bitwise 中性。保留原始模式，单独报告节点数与
   收益。`torch.compile(mode="reduce-overhead")` 留作独立变体，避免将 Inductor 融合、
   kernel 选择和 graph 收益混在一起，理由见 [decisions](../decisions.md)。

**产物**：基准 manifest、固定 token fixtures、已知限制记录。M2 完成状态沿用，
不再把任意 full/chunk 的 bitwise 相等作为 M3 的前置条件。

## 2. 先建立固定 benchmark harness

### 2.1 执行方式

| 名称 | cache / 执行 | 用途 |
|---|---|---|
| `eager` | M2 DynamicCache + eager forward，attention 读取有效长度 L | 测出当前实现的起点 |
| `static-exact` | 预分配 KV/state，attention 仍读取 `[:, :, :L, :]` view | 单独观察 cache 存储和更新方式变化 |
| `static-cap` | 与 static-exact 相同的 cache；decode attention 扫满 capacity + mask | 单独观察固定 attention shape 的代价 |
| `graph` | capture static-cap 的单 token 模型 step | 单独观察 graph replay 的收益 |

四个路径使用同一 checkpoint、dtype、prefill chunk 和 workload。prefill 都沿用有效长度
attention；`static-cap` 的扫满 capacity 只发生在 decode。分别在独立进程运行，
避免 graph pool、JIT workspace 和 allocator 历史干扰对照；不同时驻留两份模型权重。
系统 decode 共用 §2.3 的 pinned staging。M2 原生 pageable 传输若另测，单列为
`eager-original-io`，不把这项变化算成 cache 或 graph 的收益。

### 2.2 固定深度与 token 计数

- 主对照：`depth=512 / 7680`，各生成 `n_gen=512`；总长度分别为 1024 / 8192。
- prefill 消费全部 prompt，首个输出 token 从 prefill logits 采样，归入 TTFT。
  剩余 **511 次 decode forward / 511 个输出 token** 构成计时区间。
- 统一记录 `prompt_tokens`、`generated_tokens`、`timed_decode_steps`、起止 cache 长度。
  该协议下最终 cache 长度为 `depth + 511`，因为最后一个输出 token 不再 forward。
  模型和系统 decode tok/s 的分子都用 511，不能混用 512 个输出和 511 次 forward。
- 固定深度 prompt 沿用 `scripts/m2_capacity.py:fixed_ids` 的重复文本
  `The quick brown fox jumps over the lazy dog. `，截取到规定 token 长度；它只用于
  性能和容量，不能用于判断生成质量。
- 当前尚无固定深度的完整续写 fixture。实施时由 **`ca1bd2e` 的 eager runner 生成并冻结**
  greedy token trace，忽略 EOS，保证每次工作量相同。模型计时使用该 trace；
  系统计时运行真正的 greedy 自回归闭环，记录实际 token trace。发生生成分叉时，
  用相同 token 输入做数值定位，不能只比较自由生成后的 hidden。
- prompt IDs 与续写 trace 保存到 `bench/workloads/`，记录 tokenizer/template hash、
  生成 trace 的 commit 和文件 hash。以后从文件读取，不随候选 runner 重新生成基准输入。

### 2.3 两套速度与计时边界

| 指标 | 计时范围 | 方法 |
|---|---|---|
| 模型 decode tok/s | GPU 上已就绪的单 token embedding → decoder、cache/state 更新、完整 lm_head logits | `timed_decode_steps / sum(model_step_gpu_s)`；CUDA events |
| 系统 decode tok/s | 首 token 已可用 → 最后一个 token 可用；包含 host embedding gather、H2D、模型、sampling、token D2H、CPU 调度与空隙 | `timed_decode_steps / decode_wall_s`；墙钟 |
| 请求有效输出速度 | chat template/tokenization 开始 → 最后一个 token 可用，含 prefill 和 sampling | `generated_tokens / request_wall_s`；另报 TTFT、prefill 时间 |

- 模型路径可预先准备 trace 的 embedding 行；所有模式都将当前行拷入固定 GPU 输入
  buffer。**该 D2D copy 在 start event 之前**；同 stream 按序提交，使用 copy stream
  时先等待其完成事件，再记录 start event。记录测试夹具显存和 copy 时间。
- 系统 decode 的四模式共用同一 host gather → 可复用 pinned 行 buffer → 固定 GPU
  输入 buffer 流程，额外 host copy 也计入墙钟。不得预置真实自回归请求未来的 embedding；
  整份 2.543 GB embedding 始终在 host。
- CUDA events 包围模型提交区间，可能包含该区间内的设备空隙；它不等于 kernel 时长之和。
  kernel 总时间与空隙由 Nsight Systems 单独解释。
- 同一 stream 上记录 events；如使用 copy stream，明确 event 依赖。批量读取计时结果，
  避免在模型计时的每个 step 额外 `synchronize()`。系统闭环自身需要的同步照常计入。
- tokenization、模型加载、JIT、warmup、capture、日志和 detokenization 分开记录；
  性能循环不运行数值 reference hook、逐层 CPU dump 或逐步 `isfinite().item()`。
  finite/state 验证另跑，保证验证开销不混入 baseline。
- 原始 token 数包含 thinking 和停止 token；真实请求生成不足两 token 时，decode
  速度记为不适用，不能除以零或借用总输出数。

### 2.4 重复与真实 workload 分级

1. P0 固定深度按 §3.2 的矩阵执行；每项先完整 warmup 一次，再做 **5 次**测量，重建同一逻辑
   初态并重新 prefill。保留所有样本，报告中位数、min/max、标准差和逐步 p50/p95。
   分别标明 run 间波动与 step 延迟分布，不把它们混成一个指标。
2. 记录 GPU 时钟、温度、功耗、并发进程、驱动/CUDA/PyTorch/FlashInfer/Nsight 版本。
   发现明显干扰则保留原始记录、说明原因后复测，不通过修改系统设置改善数字。
3. P1 按 roadmap，从 GSM8K / MATH-500 / HumanEval / MBPP / MT-Bench **各固定 20 条**。
   实施时记录具体来源、split、revision、sample IDs、抽样 seed=0 和模板；将渲染后的
   prompt/token IDs 固化。MT-Bench 还需固定轮次规则和历史消息。
4. 真实 workload 开启 thinking，默认 `max_new_tokens=2048`，实际预算取
   `min(2048, 8192-prompt_tokens)`，记录截短预算或排除超长输入的原因。
   正常响应 EOS；分别汇总每个数据集的输出长度、速度、TTFT、停止原因和显存。
5. P2 补跑 roadmap 的采样组：temp=1.0、top-p=0.95、top-k=20、min-p=0，
   固定 RNG seed、过滤顺序和 sampler 实现；greedy 与 sampling 分开报告。
   当前 M2 的非 greedy 分支仅作普通 multinomial，不能直接标成这组配置。
6. P0 保留三条真实 smoke、固定 trace 的 16 步检查及两档完整边界检查；全量 100 条
   greedy 和采样组不阻塞 M3 关闭，仍属于后续项目报告要求。两组在最终候选上执行，
   报告混合 workload 时另给 `sum(tokens)/sum(time)`。

**P0 产物**：固定深度/smoke manifest、eager 两档原始结果、分阶段时间与显存、第一张时间线。

## 3. Static cache：存储与 attention shape 分两步适配

### 3.1 静态存储与执行方式

1. 核查锁定的 Transformers 版本对 hybrid `StaticCache` 的实际支持；若不能满足
   GDN/conv 和 device position 的需求，再实现项目内的最小 cache adapter。
   不能仅因类型名含 Static 就认为支持 graph replay。
2. KV 预分配为 16 层的 BF16 K/V，GDN 为 48 层 FP32 recurrent state，conv 为
   48 层 BF16 state。容量支持 **1024 / 8192** 两档，具体对照见 §3.2。
3. KV 按当前位置原地写入；recurrent/conv state 用固定地址原地更新。位置、有效长度
   与 RoPE/mask 的关系显式定义，区分“已缓存 token 数”和“本步 token 的位置”。
   检查每层一致、只推进一次、无越界；不能用替换 tensor 的方式更新长寿命 state。
4. prefill 仍按 128 分块，尽量直接写 static cache，避免同时保留整份 dynamic 和 static
   KV/state。确需转换时逐层迁移并释放旧 buffer，把转换峰值单独记录。
5. 先实现 `static-exact`：attention 读取有效前缀 view，mask 与 M2 一致，验证存储和
   原地更新；此路径可以有依赖 L 的 Python view，不用于 capture。记录 `repeat_kv` 后
   的 shape/stride，bitwise 是否一致以实测为准。
6. 通过后实现 `static-cap`：仅 decode 的 attention 扫满 capacity，由 device 长度和
   mask 控制可见范围；prefill 继续使用有效前缀。未写入槽初始化为有限值，防止未使用的
   NaN 经乘法污染结果。用独立 padded DynamicCache reference 验证，详见 §5.1。
7. 分开记录有效 L 与实际扫描长度：eager/static-exact 按 L，static-cap/graph 的
   decode 按 capacity；额外流量见 §6。M3 不更换 attention 数学 kernel。
8. 实现原地 reset；验证连续请求 A→B→A 与各自新请求一致。检查有效长度以外的数据
   不会影响输出；使用不同的有限填充值做隔离检查。

### 3.2 Capacity 对照

| P0 场景 | 执行方式 | 目的 |
|---|---|---|
| depth=512，capacity=1024 | static-exact / static-cap / graph；另测 eager 的动态长度基准 | 短固定深度的紧凑容量 |
| depth=512，capacity=8192 | static-exact / static-cap / graph，复用同一 eager 对照 | 量出大 capacity 的扫描和显存代价 |
| depth=7680，capacity=8192 | 四模式 | 8K baseline 与容量验收 |

eager 没有固定 backing capacity，结果标为 dynamic；不能把它写成扫满 8192。
真实请求按 `prompt + min(2048, 8192-prompt)` 选档，非空 prompt 的申请值至少为
2049，因此默认真实 workload 和三条 smoke **全部使用 8192 档**。1024 档主要服务
短固定深度测试，不能用其速度代表默认真实请求；本阶段不引入 graph 分桶切换。

**退出条件**：static-exact / static-cap 各自对照通过，reset、buffer 地址和字节账明确。
通过后再进入 capture。

## 4. CUDA Graph：固定单 token 模型 step

### 4.1 Capture 边界

- 首版 capture static-cap 的 decode；输入为固定地址的 `inputs_embeds [1,1,5120]` 与 device 位置/state，
  输出为固定地址的最后位置 logits；包括 decoder、cache/state 更新和 lm_head。
- CPU tokenization、host embedding gather、CPU 停止判断放在 graph 外；与其他三模式
  共用 pinned host 行 buffer 和固定 GPU 输入 buffer 完成 H2D。先保证依赖正确，
  embedding 的深度流水优化留给 Phase 2。
- sampling 先在 graph 外执行并计入系统速度。首版不要求整个自回归闭环在 GPU 内，
  但所有模型层需要进入 graph；只 capture GEMM 或几个层属于中间诊断结果。

### 4.2 按锁定版本核查并 dry capture

先核对 GPU 主机上安装的 5.20.2 源码与 hash，记录每项的调用位置、运行期类型、
capture 结果及最小适配。以下状态来自官方 tag 核查，不用 5.3.0 的实现推断故障：

| 检查项 | 5.20.2 已知情况 / 实施检查 |
|---|---|
| linear attention mask | 已使用 `create_recurrent_attention_mask`，模型内无旧 `_update_linear_attn_mask`；检查实际 mask helper 是否有 device tensor 转 Python bool/CPU 同步 |
| position / length | `StaticLayer.cumulative_length` 初始化后在设备上；核查 get_seq_length、RoPE 和 mask 全链路，不能一概认为返回 Python int |
| GDN/conv state | 常规更新已用 `copy_`；提前完成 lazy initialization，核查 decode 分支、reset 后标志与 buffer 地址 |
| attention | static-cap 的 shape 固定；检查 dropout=0、mask dtype、实际 repeat_kv 物化与 workspace |
| NVFP4Linear | divisor/alpha 当前逐次计算，可 capture 但会增加节点；FlashInfer JIT、workspace 和 tactic 要在 warmup 时固定 |
| HostEmbedding / sampling | host 工作在 graph 外；测试输入更新、stream 依赖和 token D2H 同步边界 |

在 static-cap 对拍通过后，先对 1024 档完成 warmup 和一次 **dry capture + 多步 replay**，
记录失败节点与位置推进情况。确认可行后，再按 §5.2 的预算检查进入 8192 档。
参考：[Qwen3_5 5.20.2](https://raw.githubusercontent.com/huggingface/transformers/v5.20.2/src/transformers/models/qwen3_5/modeling_qwen3_5.py)、
[cache_utils 5.20.2](https://raw.githubusercontent.com/huggingface/transformers/v5.20.2/src/transformers/cache_utils.py)。

### 4.3 预热、位置推进与内存

1. 先完成 FlashInfer JIT、workspace 分配及相应 shape 的 warmup；按 PyTorch 的
   side-stream warmup 要求建立依赖。capture 内不做 `.item()`、CPU gather、设备同步
   或依赖数据的 Python 分支。
2. 所有 replay 复用固定的输入、输出、KV、GDN/conv state 和位置 tensor 地址。
   device 位置值随 step 更新；不能在 capture 时把 Python 的 `get_seq_length()`
   结果固化为永远不变的位置。若由 graph 推进位置，host 循环只维护必要的逻辑计数。
3. warmup 和 capture 前后的试运行都可能涉及 state；测量前原地 reset 并重新 prefill
   正式 prompt，不能把预热后的位置/state 当作正式初态。此时 graph/pool 仍然常驻，
   必须通过 §5.2 的组合显存场景，而不能仅测 graph 创建前的 prefill。
4. 每档 capacity 单独验证 capture/replay；正式对照进程只保留本次需要的 graph，
   避免同时驻留多份 graph-private pool。pool sharing 后续按实际需求验证，不能仅为
   省显存假定任意 replay 顺序都安全。
5. graph 内产生的临时 tensor 由 capture pool 管理；显式保留必要对象的生命周期。
   检查 workspace 地址稳定、重复 replay 后 allocated/reserved 不持续增长。
6. 若有算子无法 capture，先定位具体 CPU 操作、动态 shape 或 allocator 行为，做
   最小适配并单独对拍。分段 capture 可用于定位；8K 完整模型 step 未通过时，不将
   分段结果写成 M3 graph baseline 已完成。

约束依据：[PyTorch 2.14 CUDA Graph 文档](https://docs.pytorch.org/docs/2.14/notes/cuda.html#cuda-graphs)。
graph replay 依赖固定地址和 shape，CPU 工作不会随 replay 重执行；capture pool 也有
独立生命周期，必须计入峰值。

**退出条件**：两个 capacity 下模型 step 可重复 replay，位置持续正确推进；
static-cap / graph 固定输入验证通过，graph 常驻后的真实生成、8K prefill 和 reset 正常。

## 5. 正确性验收与显存预算

### 5.1 数值验证

| 对照 | 检查 |
|---|---|
| M2 eager → static-exact | 相同有效 L；逐层 hidden、有效 KV、GDN/conv state、logits；先检查 bitwise |
| padded DynamicCache reference → static-cap | 相同 decode attention shape；独立的 cache/position/mask 簿记；先检查 bitwise |
| static-cap → graph | 同一 shape、backend、初态与输入；逐步检查 bitwise、位置及地址稳定 |
| unpadded → padded reference | 单独报告 attention 长度效应及首处分叉，不作为上述执行管理改造的通过门槛 |
| 请求 reset | A→B→A；短→长→短；与独立新请求对比，确认无历史残留 |
| 边界 | prompt 长度 1、127、128、129、300；两档容量末端与越界拒绝；至少一段含非零历史 state 的续段 |
| 真实生成 | 三条 M2 smoke，greedy、thinking、2048 上限，答案与停止规则合理 |

- 使用相同输入进行对拍，预先保存 reference token trace。按 step/layer 保存首处失败，
  避免自由生成分叉后继续比较不同输入。
- padded reference 沿用 M2 DynamicCache 的追加、位置与 state 管理；仅在 decode
  attention 计算前，将 K/V 补有限值至 capacity，并按 reference 自己的有效长度与位置
  构造 mask。prefill 保持原路径。**不复用 static adapter 的索引、位置更新或 mask 逻辑**，
  避免两侧共享错误。它是验证路径，不进入正式性能表。
- 纯 cache 搬运、位置计数和 reset 必须精确。static-exact 的前缀 view 可能不连续，
  `repeat_kv` 后预计恢复同形状布局，需实测 shape/stride/backend；相同路径先尝试
  bitwise 验收，不能仅凭模式名承诺所有环境都 bitwise。
- M2 重复运行只测重复性，不能由零噪声推出跨 shape 的非零容差。若同形状对照仍有
  差异，定位首个算子并使用独立 reference 解释；确需非零容差时，先固定依据与配置再
  继续集成，不能仅放宽阈值。不同 shape 的诊断差异也不自动证明存在或不存在实现 bug。
- 逐算子验证沿用 M2 的同 A/W dequant reference 和正确的 GDN normalization。
  对拍可分进程、逐层或分步保存 CPU 结果，避免同时驻留两份模型或完整 GPU 快照。
- 验收退出状态必须检查实际执行次数、所有数值失败、finite、dtype、cache 长度及
  reset；零检查不能成功。统计按 run/prompt/phase/step/layer 标识，独立保存快照。

### 5.2 分阶段显存

参考 M2 的 `results/m2/20261021T135649-capacity/`：8K prefill peak 15.620 GB、
decode peak 15.423 GB、reserved 15.859 GB、进程剩余 free 0.413 GB。
这不是可直接分给 graph 的预算；static cache 提前分配和 graph pool 可能增加峰值。

仅按权重、8K KV、GDN/conv state 求和约为 15.149 GB，距 M2 decode peak 约 0.274 GB。
这部分还混有 workspace 等占用，**不能直接当作 graph pool 大小**；reserved 中也有
可回收缓存。因此“叠加后只剩约 0.14 GB”只是一组 allocator 假设下的风险估计，
不是已测余量或可靠上下界，1024→8192 也不能简单按比例外推。

1. 先测 1024 档 capture 前后的 allocated/reserved/free 和内存快照；再结合 8192 档
   static-cap 的临时量与 §6 的 KV 展开字节，拆分固定 workspace 和随 capacity 增长的
   项，评估 8K capture 风险。最终 pool 占用以 8192 档实测为准。
2. P0 必测组合场景：**graph 已常驻 → 原地 reset → 7680-token prefill → 511 次 decode
   → reset 后再次 prefill**。这是最大固定深度请求的正常生命周期；检查全过程无 OOM、
   stale state 或持续内存增长。不能销毁 graph 后再 prefill 来替代这个场景。
3. 分别测 load/repack、cache 初始化、无 graph 的 prefill、warmup/capture、
   **graph 常驻后的 prefill**、decode、reset 后的 allocated/reserved peak 和
   `mem_get_info()`；各阶段开始重置 peak、结束同步，保持其他常驻对象存活。
   同时记录 end occupancy，峰值不能用阶段结束值代替。
4. 实际有 scale swizzle/repack 或 cache 转换就计入阶段，不因权重保持 packed 格式而
   省略临时 buffer。整体 peak 取各阶段最大值。
5. 账目包括权重、两档 KV capacity、GDN/conv state、输入/logits staging、workspace、
   graph pool、测试夹具和 CUDA context；用 `nvidia-smi` 辅助记录，不能用低频采样
   替代 allocator peak。
6. 若 OOM，先检查双份 cache、旧 graph/pool 生命周期、捕获中间量和 workspace；
   再评估减小 prefill chunk。修改 chunk 后 reference 使用同样配置重新对拍，性能结果
   标为独立配置，并保留原失败记录。
   改 KV dtype、state dtype 或搬 embedding 上 GPU 属于另一变体，不能作为主线静默兜底。

## 6. 按实际字节重算 SOL

补齐 `docs/sol.md`，从 manifest 和运行时唯一 tensor storage 核算，而不是继续使用
早期的 14.41 GB 估值。权重与 scale 分列，排除 vision/host embedding，避免 alias 重复计数。

对第 t 个计时 decode step，令 `L_t` 为加入当前输入 token 后的有效 KV 长度：

```text
B_ideal(t) = B_weights
           + 2 * N_full_attn * H_kv * D_head * kv_bytes * L_t   # K/V 读
           + 2 * N_full_attn * H_kv * D_head * kv_bytes         # 新 K/V 写
           + 2 * B_gdn_state                                  # recurrent 读写
           + B_conv_state_read_write
```

- `N_full_attn=16, H_kv=4, D_head=256`；主线 `kv_bytes=2`。
  GDN/conv 字节用实存 shape/dtype；固定深度计时区间的 `L_t=depth+1 ... depth+511`。
- 这是权重每步读取一次、KV/state 必需访问的逻辑模型。activation quant、临时张量、
  GQA 展开、固定 capacity 的 masked 槽访问、ShapeStableLinear padding 等额外流量
  单列；有额外流量不等于有效模型字节变大。
- `B_mean = mean(B_ideal(t))`，`SOL_tok_s = 960e9 / B_mean`，
  `logical_GB_s = B_mean * measured_tok_s / 1e9`，`%SOL = measured_tok_s / SOL_tok_s`。
  模型速度和系统速度分别代入并明确标签。
- 报告平均有效 context 的 SOL，也保留满 8K 口径。逻辑带宽与 ncu 的 DRAM 实测
  分开；Nsight Systems 本身不提供这份 DRAM 字节验证。
- M3 只产出 BF16 KV 实测。FP8 可列理论容量/SOL，明确“未实测”，不为了填表提前
  引入 FP8 attention kernel。M1 的 IQ4_XS 速度仅作外部参照。

**Eager attention 的额外流量模型**：5.20.2 的 `repeat_kv` 将 4 个 KV heads 展开到
24 个 query heads，之后再做 matmul。按原始 K/V 各读取一次、展开结果各写一次并被
matmul 各读一次估算（未计 softmax 等其他操作）：

```text
O(C) = H_kv * C * D_head * kv_bytes       # 单层、单个 K 或 V 的紧凑字节
E(C) = H_q  * C * D_head * kv_bytes       # H_q=24，展开后的字节
B_expand_model(C) = 2 * N_full_attn * (O(C) + 2 * E(C))
```

| 扫描长度 C | 紧凑 KV 读 | 展开路径总量估算 | 相比同长度紧凑 KV 的额外量 |
|---|---|---|---|
| 1024 | 0.067 GB | 0.872 GB/step | 0.805 GB/step |
| 8192 | 0.537 GB | 6.979 GB/step | 6.442 GB/step |

两档展开路径相差约 6.107 GB/step。eager/static-exact 用有效 L 代入；static-cap/graph
的 decode 用 capacity 代入。和 `B_ideal` 比较时扣除其中已计入的有效 KV 读取，避免重复。
这些是数组访问量估算，不是实测 DRAM 流量或毫秒数；cache 命中、kernel 实现和调度
会影响实际成本。两档 context 速度接近也不能单独证明 CPU-bound，需要时间线验证。

## 7. Nsight 时间线与 Phase 2 交接

1. 对 eager 起点和最终 graph 候选各采集一段 warmup 后的代表性 decode，覆盖两档
   depth。标记 host embedding、H2D、model、sampling、D2H 和 idle/NVTX 区间。
2. profile 单独运行，正式 tok/s 使用未开启 profiler 的测量。记录 graph 展开/追踪
   选项和采样步数，保存 `.nsys-rep`、导出的统计及复现命令。
3. 拆解 CPU 提交、同步、GPU kernel、内存复制和空隙；有 overlap 时按关键路径解释，
   不把所有区间相加当作墙钟。至少列出 top 5 kernel/阶段及调用次数、总时长、占比。
4. 增加 **每步 kernel 数、graph node 数（区分 kernel/memcpy 等类型）、kernel 时长
   直方图，以及 <5 µs kernel 的数量占比和累计时间占比**，并与可见空隙分开报告。
   Python op 不一定一一对应 kernel；数千节点及固定每节点开销都应实测，不能据源码
   op 数量直接推算 replay 耗时。graph 减少提交开销，但不会自动融合原有 tiny kernels。
5. 按实际时间占比确定 Phase 2 顺序，候选包括 NVFP4 GEMV、GDN/conv、attention、
   norm/quant 融合、host embedding 传输、ShapeStableLinear padding。没有数据时不预设
   哪个 kernel 必须先重写；ncu 仅在需要验证 DRAM 流量或带宽上限时追加。

## 9. 顺序与退出标准

执行顺序：**生成并冻结 P0 fixtures → eager harness + 时间线 → static-exact → static-cap
→ 1024 dry capture/内存评估 → 8192 capture 与常驻 prefill → P0 报告**。
roadmap 的 1–2 天仅为 P0 初估；以正确性、capture 可用性和显存实测为准。

| 级别 | 范围 | 与 M3 关闭的关系 |
|---|---|---|
| P0 | 固定深度四模式、独立 reference、state/reset/边界、三条 smoke、显存、SOL、时间线 | 全部通过才关闭 M3 |
| P1 | 五个数据集各 20 条真实请求，greedy | 后续报告项，不阻塞 M3；未跑时明确标记 |
| P2 | 同一 workload 的规定 sampling 组 | 后续报告项，不阻塞 M3；不能用普通 multinomial 代替 |

**P0 退出检查：**

- [ ] 固定深度/smoke fixtures 已生成并固化，首 token/forward 数、staging 和计时边界可复现。
- [ ] 四模式与独立 padded reference 的数值、cache/state、reset、边界验证通过，限制明确。
- [ ] 两档 capacity 均可完成模型 step capture/replay，三条真实 smoke 的 thinking/EOS 正常。
- [ ] §3.2 全部对照各 5 次原始数据齐全，含 depth=512/capacity=8192；两套速度和波动分开报告。
- [ ] load/repack、prefill、capture、decode 及 graph 常驻后再次 8K prefill 的峰值可解释，无 OOM。
- [ ] `docs/sol.md` 使用实际字节，BF16 实测与 FP8 理论值、逻辑带宽与物理带宽明确区分。
- [ ] eager 与 graph 的时间线、每步 kernel/node 数和时长分布齐全，Phase 2 顺序有数据支持。

P0 全部满足后将 M3 标为完成，P1/P2 独立跟踪；Phase 2 的约 80% 带宽目标不作为
本阶段的退出门槛。activation quant 的规范诊断在替换量化实现前完成。
