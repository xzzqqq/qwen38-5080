## Runner 数值验收

命令：

```bash
make m2-numeric
```

三条真实 prompt 固定 greedy 16 步，teacher forcing；每条都检查：

| 检查 | 数量 | 结果 |
|---|---|---|
| NVFP4Linear vs 同 A/W 量化 dequant reference | 400 | 0 failures；worst nrmse **0.00218**、cos 0.9999981、max_rel 0.00342 |
| activation quant 参考 vs FlashInfer | 400 | 0 failures（单列）；worst nrmse **0.0160**、cos 0.99987、max_rel 0.0714 |
| GDN core vs FP32 逐 token recurrence | 48 | 0 failures；worst nrmse **1.5e-4**、max_abs 4.9e-4 |
| GDN final state vs FP32 recurrence | 48 | 0 failures；worst nrmse **7.9e-7**、max_abs 4.8e-6 |
| lm_head dequant reference | 3 | nrmse 0.00164–0.00167、cos ≥0.9999985 |
| hidden states | 3×17 | 全部 finite，BF16 |
| cache | 3 | KV BF16、recurrent FP32、conv BF16；长度正确 |

容差：

- NVFP4Linear：`nrmse ≤ 5e-3`、`cosine ≥ 0.99999`、`max_rel ≤ 1e-2`；
- activation quant：`nrmse ≤ 2e-2`、`cosine ≥ 0.9995`、`max_rel ≤ 1e-1`
  （FlashInfer 与 PyTorch E2M1/E4M3 rounding 在真实 activation 上有约 0.4% code 不同）；
- GDN：`nrmse ≤ 1e-3`、`cosine ≥ 0.99999`、`max_rel ≤ 5e-3`。

说明：NVFP4 的 reference 用与目标相同的 FlashInfer A/W 量化结果做 dequant，
验证权重 layout、scale 和 GEMM；activation quant 的差异单独记录，不混入
NVFP4Linear 的严格容差。GDN prefill 用 chunk kernel vs FP32 逐 token recurrence；
decode 本身走同一 FP32 recurrence 路径。

## 容量与显存

命令：

```bash
.venv/bin/python scripts/m2_capacity.py --depths 512,7680
```

| depth | cache_len | prefill | decode 512 | peak alloc | reserved | free | checks |
|---|---|---|---|---|---|---|---|
| 512 | 1023 / 1023 | 0.701 s | 43.934 s（11.63 tok/s） | 14.776 GB | 14.915 GB | 1.357 GB | finite / dtype / len 全过 |
| 7680 | 8191 / 8191 | 6.586 s | 44.011 s（11.61 tok/s） | **15.620 GB** | **15.859 GB** | **0.413 GB** | finite / dtype / len 全过 |

- 最后一步 token 不再次 forward，所以 `cache_len = depth + 512 - 1`；
- KV：16 层 BF16；recurrent：48 层 FP32；conv：48 层 BF16；
- loader 直接读 packed checkpoint，没有单独的 repack 峰值；
- 8K baseline 只剩 **0.413 GB** free，DFlash2 容量会更紧。

## 已知限制

- 没有整份 BF16 reference model；数值 reference 是逐 op/逐层运行。
- activation quant 的 PyTorch reference 与 FlashInfer 有少量 rounding 差异，
  单独记录；NVFP4Linear 本身用相同 A/W 量化验证。
- GDN decode 和 prefill 使用不同的上游 kernel 路径，prefill 做了
  chunk-vs-FP32-recurrent 对拍。
- ShapeStableLinear 的 padding、GDN/conv fallback 和 lm_head 大 vocab 仍是 M3
  性能优化对象；M2 只冻结正确性。

## M3 交接

- `EagerTextRunner` 可直接作为正确性 reference；static cache / CUDA Graph 从
  同一权重和 cache 布局开始。
- 需要处理：Python chunk/decode loop、DynamicCache 变长、HostEmbedding 的
  CPU gather + H2D、ShapeStableLinear 分块/补 zero、lm_head 大 vocab、
  `causal_conv1d` / `fla` fallback。
- M3 先做 static cache，再录 graph；性能 baseline 必须与 M2 的 eager 输出对拍。
