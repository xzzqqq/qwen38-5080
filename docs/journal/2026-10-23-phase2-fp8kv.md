## 1. 结论摘要

**能把契约、数值和接线证明的部分都已经证明；端到端收益与显存收益没有任何实测
证据，不能写成“有收益”。**

已验证：

- 量化/反量化契约与独立 reference **逐位一致**（8 类输入、双入口、per-head
  独立性、±0/subnormal/saturation/中点），roundtrip nrmse **2.60%**、
  cosine **0.999660**、`max|err|/amax` **0.0308**（与实现前的 CPU 校准一致）。
- FP8 KV attention 的数值（4 长度 × 4 变体 × 2 样本 + 4 次 graph replay）：
  fused FP8 到 fp64 的 nrmse **0.00350**、cosine **0.9999939**、max_rel
  **0.00521**；fused 到 fp64 的距离只有 grouped_bmm 的 **0.54–0.56 倍**
  （即 fused 更准）。
- **FP8 + fused 接线成立**：132 次 decode 全部走 fused kernel，
  `dequant_fallback == 0`（decode 零 bf16 物化）；重复调用 bitwise、
  graph replay 4/4 bitwise、mask 隔离（改不可见槽位的 fp8 code + scale 后
  bitwise 不变）全部通过。
- 第一条路径（物化 bf16 前缀再 grouped_bmm）**实测为净回退**，见 §6；即使换成
  fused，FP8 分支每 call 仍比 BF16 慢 4–5%（转换受限），所以 FP8 目前是
  **显存/验收格式收益，不是速度收益**（见 §3.3）。

未验证（本轮硬缺口）：

- `bench/e2e/decode.py`（graph-8192 / graph-512-1024）**从未执行**；
- `smoke-graph`（三条真实 prompt 的 EOS/长度/内容 gate）**从未执行**；
- `m3_memory --only graph-8192` **从未执行**，8K 显存收益没有实测；

## 2. 冻结方案与实现

冻结方案（实现前写下，本轮未改）：

- 存储 `torch.float8_e4m3fn`，K/V 都存 FP8；
- scale 是 per (layer, kv_head, token) 的 **float32** 标量，K/V 各一套，常驻布局
  `[capacity, kv_heads]`（行 token、列 head）；
- 量化契约（全 fp32 算术）：`scale = amax/448`（amax 在该 token 的 256 dim 上取，
  amax=0 时 scale=0）、`q = rne_e4m3(clamp(x/scale))`；
- 反量化契约：`x = bf16(float32(q) * scale)`（fp32 乘一次再 cast bf16）；
- 有效长度之外的槽位 code/scale 都写 0，mask 语义不变。

实现：

| 文件 | 内容 |
|---|---|
| `runner/ops/kv/fp8.py`（新） | 契约、`quantize_kv`、`quantize_with_scale`、独立 `reference_quantize_kv`、`dequantize`（Triton 融合 + torch 回退）、`dequantize_exact`（fp64 精确参考）、`dequant_kv`、scale side channel（`kv_fp8_scale`） |
| `runner/ops/kv/_triton_dequant.py`（新） | fp8→bf16 融合反量化 kernel（一次 pass 读 fp8、乘 scale、写 bf16）；`.float()*s` 的纯 torch 版本会拆成 2–3 个 kernel，流量比 BF16 还高 |
| `runner/model/static_cache.py` | FP8 存储 + scale 常驻；decode 返回 fp8 前缀 + `[L,H]` scale，prefill 返回 torch reference 反量化的 bf16 前缀；`cache_stats`/`kv_tensors`/`kv_scale_tensors` 表达 FP8；`reset` 走 uint8 view |
| `runner/model/padded_reference.py` | FP8 的独立 dynamic reference（eager 与 padded 各一份，调用 **reference** 量化器），使 numeric-512 的 `eager→static-exact`、`padded-ref→static-cap` 仍是同 shape 的 bitwise 对拍 |
| `runner/model/decode_runner.py` | eager 在 FP8 下走独立 dynamic 存储；`harness_info` 记录 kv_format / dequant / decode 后端计数 |
| `runner/ops/attention/compact_decode.py` | 与任务 K 的 fused kernel 合并：`k_scale`/`v_scale` 从 side channel（或显式 kwargs）取，fused 在 kernel 内折叠；**decode 不物化 bf16**；`grouped_bmm`/`eager` 回退才 `dequant_kv` 并计数 |
| `scripts/m3_check.py` | `cache_gate` 按**声明格式**判定（bf16→`[bfloat16]`；fp8→`[float8_e4m3fn]`+`[float32]` scale dtype + 总字节），格式写进产物 |
| `scripts/phase2_fp8kv_check.py`（新） | op gate：`quant-roundtrip`、`attn-fp8-vs-ref`、`attn-fp8-vs-bf16`（diagnostic）、`microbench` |

**关于 `cache_gate` 的口径变更**：KV 格式由 plan §7 指定为 FP8，不是为接纳候选而
放宽。BF16 仍按 `torch.bfloat16` 判；FP8 精确核对 code dtype、scale dtype/layout
和 `kv_bytes`（含 scale）。BF16 对照可用 `PHASE2_KV_FORMAT=bf16` 完整复现
（四个执行方式回到原生 DynamicCache 语义）；本分支默认 `fp8`。

**两条消费路径**：decode（q_len==1）返回 fp8 前缀 + scale，直接进 fused kernel
（K 的 scale 乘在 QK 点积后、V 的乘在 `p` 上，零 bf16 物化）；prefill（q_len>1）
返回 torch reference 反量化的连续 bf16 前缀（8K 额外流量约 10 GB、十几毫秒），
这样 `numeric-512` 的 prefill bitwise 不依赖 Triton kernel。

## 3. 已验证的数值与接线

### 3.1 量化契约（`quant-roundtrip`，job-000045 与 job-000051 相同）

11/11 gate 通过（8 类：zeros / signed_zeros / subnormal / long_tail / random /
extremes / fp8 中点 / saturation；两条入口）：

| 指标 | 实测 | 冻结界 |
|---|---|---|
| roundtrip nrmse（正常类） | **0.026085** | ≤ 0.04 |
| roundtrip cosine | **0.999660** | ≥ 0.999 |
| `max|err|/amax` | **0.030769** | ≤ 0.05 |
| code / scale / dequant vs reference | **bitwise 全类** | bitwise |
| dequant fp32 中间值 vs fp64 精确乘积 | **bitwise** | bitwise |
| 全零 token（scale=0、code=±0）、per-head 独立性、scale `[T,H]` 连续 | 通过 | 通过 |

saturation 类（显式把 scale 缩小 16 倍触发 clamp）有 14 713 个 `|q|=448` 的 code，
其误差不计入 roundtrip 界（它测的是 clamp 路径，不是存储质量）。

### 3.2 FP8 KV attention

`attn-fp8-vs-ref`（4 长度 × 4 变体 × 2 样本 = 8 样本，另加 4 次 graph replay）：

| 候选 / 对照 | nrmse | cosine | max_rel |
|---|---|---|---|
| **fused FP8**（job-000051） | **0.003499** | **0.9999939** | **0.005208** |
| grouped_bmm on reference-dequant（job-000045） | 0.005902 | 0.9999830 | 0.011007 |
| fused(bf16 dequant) 到 fp64（相对判据的分子） | 0.002224 | — | — |
| fused(bf16 dequant) vs grouped_bmm（同 KV） | 0.005330–0.006301 | 0.999981–0.999986 | ≤ 0.00985 |
| fused FP8 vs fused BF16（格式差，diagnostic） | 0.036503 | 0.999334 | 0.043893 |

- fused FP8 到 fp64 的 nrmse 是 grouped_bmm 的 **0.54–0.56 倍**；
- `fused_calls=132`、`dequant_fallbacks=0`：FP8 decode 全部走 fused，**零 bf16
  物化回退**；
- 4/4 graph replay（L=513/8191 × 2 样本）eager↔replay bitwise、replay 稳定；
- 同输入重复调用 bitwise；mask 隔离（不可见槽位的 fp8 code/scale 改成垃圾值）
  输出 bitwise 不变；
- capacity_view（非连续 fp8 前缀 view）与 full（连续）都通过结构 gate。

### 3.3 microbench（job-000051，capacity-view 输入，逐 call CUDA event 中位数）

| L | fp8-fused | bf16-fused | fp8-grouped（物化） | dequant-only | fp8 有效带宽 | bf16 有效带宽 |
|---|---|---|---|---|---|---|
| 513 | 0.0419 ms | 0.0403 ms | 0.0889 ms | 0.0309 ms | 25.1 GB/s | 52.1 GB/s |
| 8191 | 0.0458 ms | 0.0437 ms | 0.2634 ms | 0.0816 ms | 366.6 GB/s | 767.5 GB/s |

- `fp8-fused / bf16-fused` = **0.955–0.963**：**FP8 分支每 call 反而慢 4–5%**。
  fp8 只读 16.8 MB 却只有 366 GB/s，bf16 读 33.6 MB 有 768 GB/s —— fp8 分支是
  **转换受限**（kernel 在 `tl.dot` 前把 K/V `to(float32).to(bf16)`，每元素转换的
  开销超过了省下的读带宽），不是带宽受限。
- `fp8-grouped / fp8-fused` = **2.12×（L=513）/ 5.76×（L=8191）**：fused 把
  “物化 bf16 前缀”的回退路径甩开，但仍没有赢过 BF16 fused。
- 推论（未实测 e2e）：attention 每层约 +0.002 ms（L=8191）× 16 层 ≈
  **+0.03 ms/step**；原估计的 −0.2~−0.3 ms 没有 per-call 证据支持。FP8 目前的
  确定收益是 **~0.264 GB 常驻显存（K/V 0.537→0.273 GB，含 scale）+ plan §7 的
  验收格式**，不是速度。以 `job-000050` 的 0.423 GB 为基，Fused FP8 后 8K free
  预期 ~0.69 GB（未实测）。

## 6. 第一条路径的否定结论（有价值）

“先反量化成 bf16 前缀，再走 grouped_bmm”是本任务的第一条实现路径。它的实测
（`job-000045` microbench）：

| L | fp8（dequant + grouped_bmm） | bf16 grouped_bmm | dequant 单独 | dequant 写带宽 |
|---|---|---|---|---|
| 513 | 0.0835 ms | 0.0422 ms | 0.0294 ms | 71.5 GB/s（launch 受限） |
| 8191 | **0.2635 ms** | 0.1795 ms | 0.0835 ms | 402.0 GB/s |

L=8191 每层慢 0.084 ms × 16 层 ≈ **+1.3 ms/step**。原因是物化：读 16.8 MB fp8，
却要写 33.6 MB bf16（比 BF16 直接读 33.6 MB 更贵），而且 bf16 scratch 的
write-back 无法避免。**结论：FP8 KV 只有在 attention kernel 内折叠 scale、零 bf16 物化时
才有意义；物化路径是净回退，不应再走。**

## 7. 精度风险

- per-token-head E4M3 的 attention 输出相对 BF16 的 nrmse **3.65%**、
  cosine **0.99933**（两个长度）。这会在 64 层 BF16 残差 + 401 个 W4A4 GEMM 里
  被放大，free-running greedy 的 near-tie argmax 可能翻转；`smoke-graph` 的
  EOS/长度/内容 gate 是本方案**唯一未验证的硬 gate**。
- 若 smoke 失败，按冻结规则最多换 2 组粗粒度参数（不反复调绿）：
  1. 每 128 dim 一个 scale（更细，误差约降一半，scale 字节 ×2 仍可忽略）；
  2. scale 用 bf16 存储（省 2 KB/层，但精度略降，收益很小）；
  3. per-head 而非 per-token（误差显著变大，只作为对照）。
- 不建议用“换 BF16 对照”或“放宽 smoke gate”来接纳 FP8：plan §5 明确 FP8 vs
  BF16 的差异只作 diagnostic，但 smoke 的 EOS/内容 gate 仍是 gate。

## 8. 下一轮建议

1. **判据**：把 `fused vs grouped_bmm` 的 5e-3 绝对阈值换成
   `fused 到 fp64 ≤ 1.05× grouped_bmm`（任务 K 已冻结）+
   `nrmse ≤ 1e-2`、`max_abs ≤ 4 ulp`（或直接只保留相对判据和 cand-vs-fp64）。
   实测 0.0053–0.0063 / max_abs 1–2 ulp 是预期的 bf16 score 舍入差异。
2. **job 拆分**：先只跑 `op + bench`（2 步，拿 e2e，对照 `job-000050` 的
   20.493 ms）；`smoke` 与 `memory` 各自独立 job。op+bench 的入口已经就绪，
   不再有脚本侧风险。
3. **kernel 改进（给任务 K 的 owner）**：fp8 分支是转换受限。要真正兑现 KV 读
   减半，需要让 fused kernel 原生消费 fp8（fp8 `tl.dot` / 在 MMA 流水线内做
   `cvt`，或向量化地一次转换整块），否则 FP8 只是显存/验收格式收益。
4. **e2e 预期修正**：按 per-call 数据，attention 侧约 +0.03 ms/step（中性偏回退），
   不要把 −0.2~−0.3 ms 当既定收益；真正的 e2e 收益要等 kernel 原生 fp8。
5. **显存**：KV 0.537→0.269 GB + scale 0.004 GB，无 decode scratch；以
   `job-000050` 的 free 0.423 GB 为基，预期 ~0.69 GB。这一项与 kernel 形态无关，
   建议在下一轮和 e2e 一起测。
6. **prefill**：目前用 torch reference 反量化（8K 约 10 GB / 十几 ms）；若下一轮
   TTFT 成为问题，可改用已实现的 Triton 反量化 kernel（decode 路径已验证它逐位
   等于 reference）。

## 10. 已知限制

- fp8 张量只做存储/搬运/转换：CPU 上 `index_copy_`/`clamp`/`isfinite`/`equal`
  都没有 fp8 kernel，cache 的写入/清零/拼接/pad 一律走 `view(torch.uint8)`，
  有限性检查先 `.float()`。
- scale 通过张量属性（`kv_fp8_scale`）随 cache 的 2-tuple `update` 返回，这是
  不改模型 forward 的唯一通道；`[L, kv_heads]` 布局与任务 K 的 `_scale_strides`
  兼容（也支持 `[kv_heads, L]`）。
- Triton 反量化 kernel 只覆盖 `head_dim=256`、连续 `[1,H,L,D]` 输出和
  `[L,H]` 连续 scale；其它布局静默回退纯 torch（计数在 `dequant_info`）。
- `dequant_scratch` 按 role 只保留当前 shape；graph 的 decode shape 固定，所以
  capture 之后不会替换；变长 eager/exact 路径不在 graph 内。
- 本轮 merge 带进来的 `runner/model/gated_norm_patch.py`（L 的文件）docstring 里
  有一行 `=======` 分隔线，`git diff --check` 会把它误报成 leftover marker；
  不是冲突，`py_compile` 正常。主仓库的 `43b0b73a` 已经删掉这行（`job-000050`
  就是那个 commit），本分支基 `66bac5c` 仍带它，集成时随 tip 一起消除。
