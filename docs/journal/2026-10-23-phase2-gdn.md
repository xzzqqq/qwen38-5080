## 1. 边界与设计

只替换 `torch_recurrent_gated_delta_rule` 的 `sequence_length == 1` 分支。conv1d、
`in_proj_*`、out_proj、gated RMSNorm 都不在范围内。

### 1.1 原路径的问题（数据流与字节账）

reference 是 transformers 的纯 PyTorch 展开（本机没有 `fla`/`causal_conv1d`，
`use_kernelized_func` 是 no-op）。单层单步对 `[48,128,128]` FP32 state 做：

```
state *= decay                                   (读 3.1 + 写 3.1 MB)
kv_mem = (state * k[:,None]).sum(-2)             (读 3.1 + 中间 3.1 + 读 3.1)
delta  = (v - kv_mem) * beta                     (24 KB)
state += k[:,None] * delta[None,:]               (中间 3.1 + 读 3.1 + 写 3.1)
out    = (state * q[:,None]).sum(-2)             (读 3.1 + 中间 3.1 + 读 3.1)
+ out.transpose(1,2).contiguous().to(bf16)       (12 KB)
+ update_recurrent_state 的 copy_               (读 3.1 + 写 3.1)
```

约 12 次全尺寸 pass、44 MB/层、约 2.1 GB/step；而 state 的必要流量只有 1 读 1 写
（6.3 MB/层，0.30 GB/step）。48 层 = 720 个 graph node，其中大量是 <5 µs 的
`direct_copy` / `BinaryFunctor`（M3 profile 里 93.6% 的 kernel 数量都是这一类）。

注意一个语义细节（CPU 对拍抓到，见 §6.1）：**reference 先把 state 乘 decay，再用
衰减后的 state 算 `kv_mem`**；不是常见的「先读后衰减」。

### 1.2 融合 kernel（`runner/ops/gdn/decode.py`）

一个 (v_head, v-block) 一个 program，`grid = 48 × (128/BV)`：

```
kn = l2norm(k[kh]);  qn = l2norm(q[kh]) / sqrt(128)      # kh = h // 3，FP32
S  = state[h, :, vblk] * exp(g[h])                       # 一次读入后先衰减
mem = kn^T S;  delta = (v[h, vblk] - mem) * beta[h]
S += kn ⊗ delta                                          # 原地写回同一地址
out[h, vblk] = qn^T S                                    # bf16 存到 out 槽
```

- v 维列与列之间独立（`kv_mem`/`out` 都是沿 k 维 reduction），按 v 切 block 不需要
  跨 program reduction，state 每个元素只读写一次；
- q/k 按 **head stride** 寻址（`kh*q_stride + k`），所以既能收 repeat 之前的
  `[1,1,16,128]`，也能收 repeat 之后的 `[:, :, ::3, :]` view（stride 384），两边都
  没有额外拷贝；
- `decay` 用 `libdevice.exp`（`__nv_expf`），与 `torch.exp` 在 FP32 上逐位一致；
  `tl.exp` 会落到 `ex2.approx`，不是同一个函数；
- state 原地写回、FP32、`data_ptr` 不变（static cache 与 graph replay 依赖）。

理论瓶颈是 state 带宽：0.30 GB/step 在 960 GB/s 上约 0.31 ms；实测 0.684 ms
（14.2 µs/层），即约 44% 的 DRAM 峰值，剩下的差来自 192 个 block 的 occupancy 和
`[128,BV]` tile 的行宽（BV=32 时一行 128 B）。

### 1.3 接入（`runner/model/gdn_patch.py`）

接入点是**模块级** `torch_recurrent_gated_delta_rule`：`Qwen3_5GatedDeltaNet.forward`
在调用点做全局名字查找，本机 `kernels` 未安装所以 `use_kernelized_func` 是 no-op，
因此替换模块属性即可覆盖 eager / static-exact / static-cap / padded-reference /
graph 五种执行方式，**没有复制模型源码**，prefill 走
`torch_chunk_gated_delta_rule` 完全不受影响。

- 命中条件（`_device_reason` + `_shape_plan`，全部 host 侧检查）：单 token、
  `state` 是 CUDA FP32 `[1,48,128,128]` contiguous、q/k/v bf16、`g` fp32、
  `beta` bf16/fp32、无 `cu_seqlens`、q/k 的 head 数与 `state` 匹配（repeat 之后
  48 个或之前 16 个都支持）。不满足就回原实现，原因计入 `counters.fallbacks`。
- rule 返回 `(out, initial_state)`：state 已经原地更新，"final state" 就是同一个
  buffer；随后模型调 `update_recurrent_state`，patch 在 `is` 同一对象时直接
  return（语义恒等，只在自拷贝时触发），所以既没有 3.1 MB/层的 `copy_`，也不依赖
  torch 是否对 `copy_(自己)` 做 early-out。
- `out` 槽按 `state.data_ptr()` 缓存（48 层 × 12 KB = **576 KB**，不是 6 MB）。
  graph 需要固定地址，所以首次 decode（warmup，capture 之前）分配，之后不变。
- 装载点在 `runner/loader/nvfp4_model.py`：`load_nvfp4_text_model` 返回前调用
  `install_from_env`，即所有消费者（`m3_check` / `bench/e2e/decode.py` /
  `m3_memory` / `m3_profile` / `m3_sol`）自动生效；`GDN_FUSED_DECODE=0` 关闭。
  info（含**活的** `counters`）写进 load info，因此会出现在 `check.json` 的
  `load` diagnostic 和 `bench.json` 的 `results[*].load` 里。

### 3.4 局部收益与端到端收益的对比

| 深度 | microbench 预测 | 实测 | 差 |
|---|---|---|---|
| 8192 | 3.239 ms | 3.844 ms | +0.605 ms（+19%） |
| 512 | 3.239 ms | 3.637 ms | +0.398 ms（+12%） |

方向一致、量级一致，且两个深度几乎相同（相差 0.21 ms，在短协议噪声内），与
「GDN recurrent 开销与 depth 无关」的预期吻合。

**为什么实测比 microbench 还多？** 合理解释是 microbench 低估了**参考路径在真实
graph 里的成本**，而不是高估了候选的收益：microbench 的 baseline 是 48 层独立
循环（graph pool 里同时只有一层的中间 tensor），而真实模型里这 48 层与 attention
的 workspace、NVFP4 GEMM 的 graph pool 交错，allocator 复用行为不同；参考路径每层
还要 `zeros_like(value)` 加 6 个 3.1 MB 全尺寸中间 tensor。这部分 +0.4~0.6 ms 没有
单独归因，登记为「未完全解释」，不把它算成候选的额外收益。

## 4. 设计取舍

1. **保留 `repeat_interleave`，不复制 `forward`**。模型在 rule 之前对 q/k 做
   `repeat_interleave(3, dim=2)`（96 个 tiny kernel，按 M3 profile 的 unrolled copy
   均值 1.56 µs 估算约 0.15 ms/step，未单独实测）。要彻底省掉
   它必须复制 45 行 transformers `forward`。不这么做的理由是 gate 的盲区：`m3_check`
   的三组 bitwise 都是**同实现自比**，复制出来的 `forward` 若有偏差，会一致地错且
   全绿；而 patch 一个函数则把所有风险收敛到已有独立 gate 的那一个 kernel。这 0.15 ms
   留在桌上，符合「一个方向、先把正确性证据做扎实」的取舍。
   代价已量化：0.15 / 3.84 ≈ 4%。
2. **`libdevice.exp`**：`tl.exp` 在 triton 3.8 落到 `ex2.approx.f32`；`libdevice.exp`
   是 `__nv_expf`，与 `torch.exp` 同一实现（PTX 里仍是 `ex2.approx.ftz` + 范围处理）。
   换掉之后 decay 与 reference 逐位一致，代价是 PTX 多 15 行、每层多 4 次标量 exp
   （被 state 带宽掩盖，实测无差别）。
3. **`update_recurrent_state` 短路**：kernel 原地写完后返回同一个 buffer，若不断路，
   每层会多一次 3.1 MB 自拷贝（48 层 = 0.30 GB/step，约 0.3 ms，正好是收益的 8%）。
   短路条件用对象恒等（`is`），对原路径完全无影响。
4. **`out` 槽按 `data_ptr` 懒分配**：48 × 12 KB，capture 前首次 decode 时建立
   （warmup 早于 capture），地址固定、graph 内无分配。相比「在 loader 里预分配 48 个」
   少了一层对 cache 生命周期的假设；代价是依赖「首个 decode 必须在 capture 之前」
   （见 §5）。

## 5. 限制与已知问题

- **`out` 槽的前提**：如果某个未来 runner 在**没有**先做一次 decode 的情况下直接
  capture，槽会在 capture 期间分配（进 graph private pool，功能仍正确但地址不再
  属于普通 pool，且 `out_bytes` 统计会偏）。现有所有入口都先 warmup（`GraphDecodeStep`
  强制 warmup 并校验 cache 前进），因此不触发。
- **`load.gdn_decode.out_slots/out_bytes` 是 install 时刻的快照**（0），只有
  `counters` 是活的。要判「融合是否执行」看 `counters`；要判 out 槽看 op 的
  `patch:out-slot-cache`。这是本轮留下的一个不理想字段，改动它需要重跑产物，故未动。
- **`GDN_FUSED_DECODE=0`** 回退开关只在 `install_from_env` 读一次；已经装上的进程中途
  改环境变量无效。
- **依赖 Triton 3.8 + sm_120a**：kernel 用 `libdevice.exp`、`tl.rsqrt`、constexpr
  head stride；换 GPU（非 Blackwell）或换 Triton 大版本需要重编/复测。首次编译
  约 1–2 s（3 组参数各一次），已计入 op job 耗时。
- **conv 未纳入**：`causal_conv1d_update` 的纯 torch fallback（`conv_state` 更新 +
  depthwise conv + SiLU）仍是逐层的多个 tiny kernel，本轮没碰。
- **`g`/`beta` 的上游计算**（`-A_log.exp()*softplus(a+dt_bias)`、`b.sigmoid()`）仍在
  eager 里每步执行，未融合。
- **head 映射的判据**依赖 `ratio = num_v_heads // num_k_heads`（本模型 3）。若未来
  出现非整除或 per-layer 不同的 ratio，`install()` 会拒绝（`ratios` 必须唯一），
  走回原路径而不是猜。
- `q/metrics` 里 `max_rel` 用最大绝对误差除以 reference 的 absmax（与
  `runner/ops/nvfp4/reference.error_metrics` 同口径），不是逐元素相对误差。

## 6. 失败记录

### 6.1 CPU 对拍抓到：decay/kv_mem 顺序（未提交到 GPU）

最初按常见 DeltaNet 写法实现成 `kv_mem` 先算、再对 state 乘 decay。CPU 上用
K=8/V=8、NV=NK 的小 shape 复刻 reference 逐位对比，state 最大差 0.0408、
nrmse 6.3e-2——被抓住。改成「先 decay，再用衰减后的 state 算 `kv_mem`」后
state 逐位相等、out 逐位相等。**教训**：GDN 的 decay 语义与 FLA 公式记忆不同，
reference 必须先逐位复刻再写 kernel。

### 6.2 `a80029d`：head-count 判定按 repeat 之前写（960/960 fallback）

第一版 `_fallback_reason` 用 `query.shape[-2] * ratio == state.shape[1]`（16×3=48）
判定，但真实调用点传进来的是**已经 repeat 过的 48 个 head**（48×3≠48），于是
`job-000023-562cfe5b` 里 960/960 次调用全部以 `head-count` 回退，bench 逐位等于
baseline（44.329 / 31.840 ms），收益为 0。

- 根因：条件检查用了「repeat 之前」的形态，而 `_decode` 里的 `[:, :, ::3, :]` 是按
  「repeat 之后」设计的，两者不自洽。
- 修复（`b5201c1`）：把形状检查拆成与设备无关的 `_shape_plan`，主路径按
  `value.shape[-2] == state.shape[1]`（48）判定，`_qk_view` 负责 `::ratio` 切片；
  同时兼容 repeat 之前的 16-head 形态。新增原因码 `qk-shape-mismatch` /
  `value-head-count` / `head-k-dim` / `head-v-dim`，便于下次一眼定位。
- **为什么第一轮没抓到**：`m3_check` 的三组 bitwise gate 都是同实现自比，patch 完全
  没生效时它们照样全绿。真正抓住它的是 load diagnostic 里的活计数（`fused=0,
  reference=960, fallbacks={head-count: 960}`）。
- 因此本轮补了两层防线（`e6bd6c7`）：
  1. **产物级 gate**：op 的新 case `patch-wiring-real-shapes` 用真实 config 的
     **meta** GDN 模块 + 真实 CUDA 张量走 patch 的模块级入口，把
     `patch:fused-path-executed`（`fused==96, reference==0, fallbacks=={}`）变成
     可直接判定的 gate；`coverage:shape-plan-real-call` 用真实调用点形状
     `[1,1,48,128]` 断言 `_shape_plan(...) is None`，就是这条 bug 的回归测试。
  2. **CPU 回归单测**（`.tmp` 内、不入库）：`_shape_plan(post-repeat 48 heads) is None`、
     `_qk_view` 取回 16 head（stride 384、逐位等于 repeat 前）、4 个错误形状的原因码，
     以及 `_fallback_reason` 的检查顺序。

### 6.3 `job-000013`：队列执行器加载了旧 KINDS（非代码问题）

首次提交被 serve 以「`steps[0].kind 必须是 check/bench/memory/profile 之一`」在
0.09 s 内拒绝。原因是 GPU 主机上的 serve 进程启动于 `1ac7460`（新增 `op` kind）之前，
执行期重放校验用的是进程内旧表；重启 serve 后 `job-000017` 正常。这一条只作为
harness 记录，与候选无关。

## 9. 下一步建议（GDN 方向）

按收益/风险排序：

1. **把 conv step 也纳入融合（下一个边界）**。`causal_conv1d_update` 仍是纯 torch
   fallback：`conv_state` 拼接 + depthwise conv(kernel=4, 10240 channel) + SiLU，每层
   至少 3–4 个 tiny kernel，48 层约 150–200 个 node。M3 profile 里
   `unrolled_elementwise<direct_copy>` 706 次/step 的大头就在这类逐层小拷贝上。
   它和 recurrent step 共享 `mixed_qkv` 这条数据流，可以在同一个 kernel 里顺带算掉，
   但要先冻结 `conv_state`（BF16）在原地滚动更新的语义与边界（首个 token 的零填充）。
2. **把 `gated RMSNorm(core_attn_out, z)` 融进 out_proj 的输入准备**。现在是
   `norm`（reduce + SiLU gate + 乘）+ `out_proj`（NVFP4 GEMM）两段，norm 的
   `[6144]` per-layer reduce 是纯延迟；把 norm 的 reduction 与 GEMM 的 activation
   quant（`quantize_with_block_size`）合成一个 kernel 可以省一次读写，但要注意
   E2 里 activation quant 的 rounding 语义尚未冻结（任务 E）。
3. **`g`/`beta` 的预计算**：`-A_log.exp()*softplus(a+dt_bias)` 与 `b.sigmoid()`
   每层每步都在 eager 里算（a/b 已是 ShapeStableLinear 的输出），可以并进
   `in_proj_a/b` 的 epilogue 或与 conv kernel 合并；量级小（≈0.1 ms/step），优先级低。
4. **不建议**继续在本 kernel 上参数细调：`bv32-w4` 与 `bv64-w8` 差 3%，`bv16-w2`
   差 19%，再调也只在 0.68 ms 的池子里；真正的下一块时间在 48 个 kernel/step 之外
   （conv、norm、GEMM）。
