## 2. 设计与数据流

模型 decode 时 `q_len==1`、`num_key_value_groups = 24/4 = 6`，第 `j` 个 KV head
对应 q head `[6j, 6j+6)`。HF eager 先 `repeat_kv` 把 4 个 KV head 物化成 24 份
（每层 K/V 各 100 MB @8192），再走 16 路 batched matmul。候选直接读
`[1,4,L,256]` 的 K/V：

```text
q [1,24,1,256] --view--> [4,6,256]
k [1,4,L,256]（可能是 capacity buffer 的前缀 view）
  -> bmm(q_g, k^T)                  -> scores [4,6,L] bf16
  -> * scaling -> + additive mask
  -> softmax(dim=-1, dtype=float32) -> bf16
  -> bmm(probs, v)                  -> [4,6,256]
  -> reshape [1,24,1,256]（第 6j+i 行就是 q head 6j+i）
```

数值路径与 HF eager 逐项对齐，只改变 reduction 的分组：`bf16 matmul ->
*scaling -> + mask -> fp32 softmax -> bf16 -> @V`。因此 local gate 用 float64
reference 定容差，而不是和旧 eager 输出比 bitwise。

实现位置：`runner/ops/attention/compact_decode.py`
（`compact_gqa_decode_attention`、`repeat_kv` / `eager_gqa_decode_attention`
baseline、`reference_fp64`、`install` / `uninstall`）。

**接线选择**：patch `transformers.models.qwen3_5.modeling_qwen3_5.eager_attention_forward`
（模块全局）。理由：`Qwen3_5Attention.forward` 在调用时从模块全局取它作为
`ALL_ATTENTION_FUNCTIONS.get_interface` 的 default，而本项目
`_attn_implementation == "eager"`，所以一处替换覆盖 eager / static-exact /
static-cap / graph 四种执行方式；比复制整个 `Qwen3_5Attention.forward` 侵入小，
也不会碰到 vision tower（`num_key_value_groups==1` 自动回退）。回退条件集中在
`_attention_interface`：`q_len>1`、`groups==1`、`dropout>0`、bool mask、mask
长度不匹配、CPU tensor、`PHASE2_ATTN_DECODE=eager`。prefill 完全走原 eager，
未改任何 prefill 语义。

接入点：`runner/loader/nvfp4_model.py` 在模型构造后调用
`install_compact_attention()`，并把 `decode_attention` 写进 load info（出现在
check/bench 的 load diagnostic 里）。

**为什么先做分组 bmm 而不是 Triton**：本方向先用最小改动验证“消除物化”的
端到端收益；实测（§6）attention 在 8K 只剩约 1.0 ms/step（约 3%），
Triton split-K + online softmax 即使再快一倍也只值 ~0.5 ms，性价比低于
B/C（NVFP4 GEMM）和 D（GDN）。如果后续 profile 显示 K/V 读带宽仍是瓶颈，再在
同一方向内替换实现。

## 3. 冻结容差与调整理由（按时间顺序）

容差在实现候选的同一个 commit `914b001` 里冻死，早于任何 GPU 候选结果：

```python
TOL_NRMSE = 1e-2          # 绝对 sanity：约 2x 冻结 baseline 的 BF16 误差底噪
TOL_COSINE = 0.9999
TOL_MAX_REL = 2e-2
TOL_BASELINE_RATIO = 2.0  # 主判据：候选不超过 baseline 到 fp64 距离的 2 倍
TOL_DIRECT_NRMSE = 5e-3   # 候选 vs baseline 直接比较
```

- reference：同样 q/k/v（转 fp64）、显式 mask、softmax 全程 fp64；
  `nrmse = ||cand-ref|| / ||ref||`，`cosine` 为展平后的余弦，
  `max_rel = max|diff| / max|ref|`（与 M2 的 `max_rel` 同公式）。
- 主判据是**相对**判据：候选到 fp64 的 nrmse ≤ 2 × baseline（`repeat_kv` +
  matmul）到 fp64 的 nrmse；另加候选 vs baseline 直接 `nrmse ≤ 5e-3`。
- 调整记录：最初按建议写 5e-3 / 0.99999 / max_abs 1e-2。实现完成后、**在提交
  GPU job 之前**用 CPU 复跑同一组输入（5 个 L、4 个变体、2 个样本）发现：
  L=1025 时**冻结的 eager baseline 自己**就是 nrmse 5.48e-3、cosine 0.9999855，
  过不了 5e-3 / 0.99999；L=1/2 的绝对 `max_abs` 也被 BF16 输出量化顶到 1.3e-2
  （|out|≈3 时 bf16 ulp 就是 1.6e-2）。这不是候选的问题，是建议阈值低于
  BF16 的误差底噪。因此把绝对 sanity 判据放宽到约 2× 底噪（1e-2 / 0.9999 /
  max_rel 2e-2），主判据保持相对判据与直接比较。该决定写在脚本 docstring 与
  `op.json` 的 `tolerances_frozen_before_candidate` 字段里。
- GPU 结果（`job-000020`）事后验证了这个量级：L=1025 候选/ baseline 的 nrmse
  分别是 5.160e-3 / 5.158e-3，cosine 0.9999867，与 CPU rehearsal 的预判一致。
  调整发生在看到该结果之前，不是事后放宽。

## 4. 正确性证据：op（`job-000020` step 0，2.0 s）

7 个 case、每 case 24 gate，共 **128/128 通过**。每档 L ∈ {1,2,513,1025,8191}
覆盖 4 个输入变体：

- `full`：K/V 长度 L、连续、全可见；
- `partial_mask`：8192 capacity buffer 的 `[:, :, :L]` view + 加性 mask
  （可见前缀 `visible(L)`，L>513 时 513）；
- `capacity_view`：同一个 capacity 前缀 view、不加 mask（static cache 的非连续
  batch stride）；
- `cap_mask`：K/V 长度 = capacity 8192、只让前 `min(L, 513)` 个 key 可见，
  即真实 `static-cap` decode 的 shape（L=8191 就是 7680+511）。

| L | nrmse（最差） | cosine（最低） | max_rel | baseline nrmse | 候选/ baseline | 候选 vs baseline |
|---|---|---|---|---|---|---|
| 1 | 0 | 1.0000000 | 0 | 0 | — | 0 |
| 2 | 2.436e-3 | 0.9999971 | 4.358e-3 | 2.436e-3 | 1.000 | 0 |
| 513 | 4.251e-3 | 0.9999910 | 5.664e-3 | 4.251e-3 | 1.00006 | 9.50e-5 |
| 1025 | 5.160e-3 | 0.9999867 | 7.830e-3 | 5.158e-3 | 1.00045 | 3.16e-4 |
| 8191 | 4.565e-3 | 0.9999896 | 5.290e-3 | 4.566e-3 | 1.000 | 3.82e-4 |

- 结构 gate：`capacity_view` 确实是 `stride(1)=capacity*head_dim` 的非连续
  view；`full` 连续。
- mask gate：把不可见区的 K/V 改写成不同的有限值（4.0 / −2.5），候选输出
  **bitwise 不变**（bf16 min 掩码在 fp32 softmax 里 exp 后是精确 0）。
- `L1` 全 0 是预期：单 key 的 softmax 权重精确为 1，输出就是 V 的 bf16 值。

## 5. 正确性证据：check `graph-1024`（`job-000020` step 1，118.8 s）

24/24 gate 通过。逐项核对后的组成（不是被 coverage 计数掩盖）：

- cache/结构：`static-cap: cache 布局 / finite / cache length / layer counts /
  forward 数`；
- graph 语义：`capture 不推进位置`、`entry→capture 增量 == warmup 步数`、
  `warmup 推进了 static cache`、`正式初态长度`、`decode 后长度`、
  `replay 写入 static KV 槽`、`logits 地址稳定`、`reset 后 prefill logits 一致`、
  `reset 后 replay 结果一致`、`输入 buffer 影响输出`；
- **bitwise**：`graph: 逐步 logits bitwise`、`graph: prefill logits == static-cap`、
  `static-cap->graph: logits / kv.keys / kv.values / conv / recurrent`（全部
  `max_abs = 0.000e+00`）；
- coverage：`coverage: 必测项齐全`。

**scope 修正**：这 24 项属于 `scenario_graph`，其中 bitwise 项是
`static-cap → graph` 方向。`eager → static-exact`、`padded-ref → static-cap`、
`padded-fill3 vs fill0` 位于 `numeric-512` / `numeric-8192`，本轮**没有跑**，
所以“三种同 shape bitwise gate 全过”目前只证明了 static-cap→graph 一组，
另外两组仍是集成阶段必须补的 gate（建议 `m3_check --only numeric-512`，必要时
`numeric-8192`）。op 层已用 `repeat_kv` baseline 直接对拍（候选 vs baseline
nrmse ≤3.82e-4），因此风险主要剩“不同 cache 路径的 batch stride 是否改变
cuBLAS kernel 选择”这一点。

诊断失败 `graph: 逐步 argmax 与冻结 trace 一致` 是 M3 已记录的既有现象
（free-running greedy 跨数值模式会因 64 层 BF16 残差灵敏度分叉，
[decisions](../decisions.md) 2026-10-21），只作 diagnostic，不是 gate。

## 6. 性能：8K 短协议与 microbench

同协议（commit 均在 `op` kind 之后、32 步 × 1 次、chunk 128、warmup 3、
`graph-8192` depth 7680 / capacity 8192）：

| 项 | baseline `job-000012` | 候选 `job-000020` |
|---|---|---|
| step p50 / p95 ms | 44.33 / — | 31.63 / 31.65 |
| step min / max ms | — | 31.60 / 31.71（std 0.018） |
| 系统 tok/s | 22.54 | 31.58 |
| prefill s | — | 7.25 |
| peak allocated / reserved GB | 15.287 / 16.056 | 15.287 / 15.867 |
| free GB | 0.119 | 0.308 |

microbench（`op.json`，单层，capacity 8192 前缀 view，逐次 CUDA event 中位数）：

| L | candidate ms | baseline ms | 倍率 | 候选带宽 | baseline 同公式 |
|---|---|---|---|---|---|
| 513 | 0.0432 | 0.0535 | 1.24× | 48.6 GB/s | 39.3 GB/s |
| 8191 | 0.1788 | 0.8565 | 4.79× | 187.6 GB/s | 39.2 GB/s |

有效带宽 = `2 * 4 * L * 256 * 2` 字节 / 时间（候选只读一遍 K+V）。

**端到端节省（12.70 ms）大于 microbench 外推（0.6777 ms/layer × 16 = 10.84 ms）
的原因**：microbench 的 K/V 是 8192 capacity buffer 的**前缀 view**，
`bmm` 对非连续 batch stride 的输入很可能先做一次 materialize，候选那 0.1788 ms
里含额外拷贝；真实 `static-cap` 8K 的 K/V 是**连续**的整块 buffer。按 M3 profile
的旧 attention 成本 13.7 ms/step（repeat_kv 9.4 + QK 2.2 + attn@V 2.1）反推，
候选在模型里只剩约 **1.0 ms/step**（16 层 × 0.0625 ms），对应
33.55 MB/layer ÷ 0.0625 ms ≈ **537 GB/s**，已经接近 5080 的实测可用带宽。
也就是说 microbench 的数字对候选是偏保守的；static-exact 模式（前缀 view）
会付那次拷贝，但那是验证口径，不是性能路径。

短 context：`graph-512-1024` 本轮**未测**。microbench L=513 只省
0.0103 ms/layer ≈ 0.16 ms/step（约 0.5%），预期短档基本持平；正式数字留给
集成确认（建议同协议 `--only graph-512-1024 --steps 32 --repeats 1`，历史口径
31.84 / 短协议 31.85 ms）。

## 7. 显存

peak allocated 与 baseline 完全一致（15.287 GB），peak reserved 从 16.056 GB
降到 15.867 GB（−0.189 GB），free 相应从 0.119 涨到 0.308 GB。graph capture pool 里原本为每层 `repeat_kv` 物化的
`[1,24,8192,256]` K/V（每层各 100 MB）不再分配，新增的
`[4,6,8192]` 级临时（bf16/fp32，<1 MB/层）远小于被移除的部分。对后续 FP8 KV
是净利好：现在 attention 只占约 3%，FP8 能省的绝对时间也相应变小，但显存余量
增加有助于容量与 graph pool。

## 8. 剩余 8K 时间账（估算）

以 31.63 ms 为总量，按 M3 profile（`results/m3/20261022T015940-m3-profile/`）
和本 microbench 估算，**不是本轮新 profile**：

| 项 | 估算 ms | 占比 | 依据 |
|---|---|---|---|
| NVFP4 GEMM（401 次 `mm_fp4`） | ~20.7 | 65% | M3 graph-512 profile，本候选不改 GEMM |
| 紧凑 attention（16 层） | ~1.0 | 3% | 13.7 − 12.7；≈537 GB/s |
| 其它 kernel（GDN conv/recurrent/out_proj、norm、activation quant、ShapeStableLinear、lm_head 等） | ~9.0 | 28% | M3 graph-512 非 GEMM kernel 合计 9.0 ms |
| graph 内部空隙 | ~1 | 3% | graph-512 是 31.84 wall vs 29.7 kernel |

结论：attention 已不是主战场。8K 的下一批收益应来自 B/C（GEMM 20.7 ms，
72.5% 峰值带宽）与 D（GDN 的小 kernel 数量），E 的 norm+quant 融合是第三顺位；
A 方向若还要继续，只值 attention 那 ~1 ms 的一部分。
